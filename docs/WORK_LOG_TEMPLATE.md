# 작업 기록 양식

새 작업은 `CHANGELOG.md`에 날짜/ID를 추가하고 아래 항목을 채운다. 설계가 바뀌면 `DECISIONS.md`, 실제 확인이 있으면 `VERIFICATION.md`, 남은 문제가 있으면 `ISSUES.md`도 연결한다. 이번에 변하지 않은 문서를 의미 없이 다시 쓰지 않는다.

```markdown
## YYYY-MM-DD / Hxx. 작업 제목

### 요청과 완료 기준

- 사용자 요청:
- 기대 입력 → 처리 → 출력/상태:
- 이번 범위와 범위 밖:

### 구현과 연결

- 변경 파일/클래스/메소드:
- 추가 기능 호출 위치:
- 전달받는 값과 반환값:
- 기존 데이터/기능에 미치는 영향:

### 설계 변경과 이유

- 이전 방식:
- 선택한 방식과 이유:
- 단점·제약:
- 관련 Dxx:

### 실제 확인

- 수행자: 학생 직접 | 개발 지원 도구 자동 실행 | 동료
- 환경/작업 위치:
- 실행 명령 또는 수동 입력 순서:
- 기대 결과:
- 실제 출력·상태·종료 코드:
- 결과: 통과 | 실패 | SKIP | 미실행
- 증거 파일/관련 Vxx:
- 이전 결과를 재사용했다면 출처와 생성일:

### 미완료와 다음 행동

- 아직 막힌 부분 또는 미검증 항목:
- 영향:
- 다음에 할 일과 완료 기준:
- 관련 Ixx:
```

## 작성 원칙

- 실행하지 않은 테스트, UI 조작, 동료 검토, 학생 본인의 이해 확인을 완료로 쓰지 않는다.
- 예상 결과를 실제 결과처럼 쓰지 않는다. 자동 테스트·Swing 렌더링·실제 사용자 조작을 구분한다.
- 통과 숫자는 그 실행의 출력만 적고 과거 숫자와 합산하지 않는다. 삭제된 요구사항의 검사는 대체/폐기로 표시한다.
- 복구한 과거 내역은 회고 기록임을 밝히고 날짜·소요 시간·커밋을 추측하지 않는다.
- 실패한 시도도 원인·수정·재확인과 함께 남긴다. 미검증을 실패로, 범위 밖을 미구현 버그로 섞지 않는다.
- 증거는 일반 `data` 파일 대신 테스트용/샘플 데이터를 사용한다.
- 수업 문서에는 사용자의 실제 요구 변경과 개발 지원 도구 사용 범위를 사실대로 기록한다.
