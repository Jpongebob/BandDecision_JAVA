# BandDecision 개발 문서

작성 기준: 2026-11-19 · Java 17 Swing 데스크톱 앱

이 문서는 2026-2 Java 12주차 개발 문서 평가 기준의 여섯 항목에 맞춰 현재 구현과 확인 결과를 정리한다. 발표 시연에는 `-Demo`의 가상 데이터를 사용한다. 상세 변경과 검사 명령은 [변경 이력](CHANGELOG.md), [설계 결정](DECISIONS.md), [검증 기록](VERIFICATION.md)에 남겼다.

## 1. 문제와 사용자 시나리오 — 15%

밴드의 일정 담당자는 멤버가 모두 모이기 어려운 상황에서 합주 날짜와 곡을 정해야 한다. 날짜별 불참과 미응답을 구별하고, 곡의 찬반뿐 아니라 각 멤버의 실력 대비 난이도를 함께 봐야 한다. 확정 뒤 응답이 바뀌어도 당시 결정을 확인할 기록이 필요하다. 기존 콘솔 메뉴는 이 정보를 비교하기 어려웠다.

BandDecision은 담당자가 한 PC에서 멤버별 응답을 대신 입력하는 로컬 앱이다. 기본 6명에서 추가·삭제해 1~64명으로 운영하며 같은 파트를 여러 명이 맡을 수 있다.

| 사용자 행동 | 프로그램의 결과 |
|---|---|
| 달력에서 멤버별 가능·불가·미응답을 입력 | 그 날짜의 전원이 응답하면 가능 인원순으로 날짜 추천 |
| 후보곡 난이도와 멤버별 찬반을 입력 | 전원 투표와 찬성 기준을 충족한 곡을 추천 점수 내림차순으로 추천 |
| 추천 날짜·곡과 장소를 확인해 확정 | 참석·불참·사유·곡·장소를 당시 내용으로 보관 |

## 2. 요구사항과 완료 기준 — 20%

P0는 합주 결정을 위한 필수 기능, P1은 사용 편의 기능이다. 완료 기준은 자동 검사로 확인 가능한 동작을 적었다.

날짜·곡 결정과 재실행 후 기록 유지가 사용자 목표에 필수이므로 P0로 정했다. 화면 편의·되돌리기·Demo는 이 흐름의 사용과 시연을 돕는 P1로 두었다. 검사 근거의 기능 메서드는 `AcceptanceTest`, 화면·되돌리기는 `GuiSmokeTest`에 있다.

| ID | 구현 범위와 완료 기준 | 검사 근거 |
|---|---|---|
| R01 P0 멤버 | 1~64명 추가·삭제, 이름·파트·실력 1~5 수정. 같은 파트 허용, 마지막 1명 삭제 거부. | `smallBands()`, `dynamicMembers()` |
| R02 P0 일정 | 오늘~다음 달 말일까지 하루·기간·월 전체 응답. 미기록은 미응답, 지난 날짜 편집 금지. | `attendance()`, `GuiSmokeTest` |
| R03 P0 날짜 추천 | 해당 날짜 전원 응답·가능 1명 이상. 가능 인원 내림차순, 동률은 날짜 오름차순. | `DateRecommender` |
| R04 P0 곡·투표 | 곡 등록·수정·삭제, 멤버별 난이도와 찬반. 반대 사유 필수. | `songs()`, `songManagement()` |
| R05 P0 곡 추천 | 전원 투표·전체 멤버 2/3 이상 찬성. 개인 부담 `max(0, 난이도−실력)`의 합으로 점수 `3×찬성−2×총부담` 계산. 점수↓, 찬성↓, 총부담↑, 내부 ID↑ 순. | `songs()`, `SongRecommender` |
| R06 P0 계획 | 추천 날짜·곡을 최종 확인하고 부분 참석에 동의해 확정. 최대 5개 저장·수정·삭제, 장소 기록. | `plans()`, `planManagement()` |
| R07 P0 저장 | 변경을 UTF-8 v3 파일로 저장·복원. 손상 파일 거부, v1/v2 전환 시 원본 보관. | `persistence()`, `smallBands()` |
| R08 P1 화면 | 일정·곡/투표·계획·설정 연결. 공통 멤버 선택, 날짜와 확정 상태 구별. | `GuiSmokeTest`, 화면 렌더 |
| R09 P1 되돌리기 | 마지막 일정 응답 변경 한 건을 복원하고 저장. | `completionAndUndo()` |
| R10 P1 Demo | 최초 실행 때 가상 일정·곡 8개·계획 2개를 별도 파일에 생성, 재실행 시 유지. | `DemoData`, 저장 검사 |

## 3. 프로그램 설계 — 20%

| 구성요소 | 책임 |
|---|---|
| `Main`, `DataStore` | 실행 모드에 맞는 파일을 읽거나 생성하고 변경 내용을 안전하게 저장 |
| `DesktopUI`, `WorkspaceView`, `ScheduleCalendarPanel` | 메뉴·달력·입력·확인창과 화면 갱신 |
| `AttendanceService`, `DateRecommender` | 멤버별 날짜 응답·사유를 관리하고 날짜 추천 |
| `Song`, `SongService`, `SongRecommender` | 곡 난이도·투표를 보관하고 추천 자격·점수 계산 |
| `BandDecision`, `RehearsalPlan` | 멤버 관리, 확정 직전 재검증, 확정 당시 계획 스냅샷 보관 |

멤버 배열의 인덱스는 각 날짜의 응답·사유와 각 곡의 난이도·투표·반대 사유에서 같다. 멤버를 삭제하면 이 배열들의 같은 인덱스를 함께 제거한다. 확정 계획은 독립 복사본이므로 현재 멤버나 응답을 바꿔도 자동으로 바뀌지 않는다. 저장 파일은 멤버 수·날짜·곡·계획을 v3 형식으로 보관한다.

실행 흐름은 **파일 읽기 → GUI 입력 → 날짜·곡 추천 → 담당자 최종 확인 → 확정 계획 저장**이다. 개인의 ‘응답 완료’는 오늘~다음 달 말일 전체를 답했는지, 날짜 추천은 해당 날짜에 전원이 답했는지를 각각 판단한다.

예를 들어 6명 중 한 명만 미응답인 날짜에 마지막 멤버가 ‘가능’을 입력하면, `DesktopUI`가 달력 입력을 받아 `AttendanceService`의 해당 날짜·멤버 응답을 바꾼다. `DateRecommender`는 전원 응답과 가능 인원을 계산해 결과를 반환하고 화면이 갱신된다. 확정 시 `BandDecision`이 날짜·곡 ID로 미리보기를 만들고, 담당자 동의 뒤 다시 조건을 검증해 `RehearsalPlan`을 보관한다. `DataStore`는 변경 내용을 저장한다. 확인 취소나 추천 조건 위반이면 새 확정 계획을 만들지 않는다.

## 4. 피드백과 설계 변경 — 15%

| 피드백·점검 | 변경 내용과 이유 |
|---|---|
| 전원이 겹치는 날이 적음 | 불가능 날짜만 입력하던 방식에서 날짜별 가능·불가·미응답으로 변경. 무응답을 가능으로 잘못 세지 않도록 함. |
| 콘솔이 복잡함 | 달력 중심 GUI와 사이드바 멤버 선택으로 변경. 일정·투표·계획을 한곳에서 비교하도록 함. |
| 6명 미만과 같은 파트 중복 필요 | 1~64명 추가·삭제와 같은 파트 여러 명을 지원. 삭제해도 남은 사람의 응답·투표 연결을 유지함. |
| 확정 계획 관리·장소 필요 | 최대 5개 계획의 수정·삭제·장소와 달력 표시 추가. 당시 결정은 스냅샷으로 보존. |
| 개발 지원 도구의 GUI 검사 실패 | 멤버 선택기 갱신 중 이전 인덱스를 참조한 오류를 발견하고 배열 교체 순서를 수정. 재검사 통과. |

위 피드백은 사용자 대화와 개발 지원 도구의 점검에서 얻었다. 12주차 자료의 **동료 직접 사용 검토는 아직 실시 기록이 없다.**

설계·코드 작성과 오류 수정, 검사 실행, 문서 정리에 생성형 AI 개발 지원 도구를 사용했다. 지원받은 변경과 실행 결과는 변경 이력·검증 기록에 남겼다. 이 문서의 자동 검사 결과는 지원 도구가 실행한 결과이며, 학생 본인의 직접 시연과 구두 설명 준비는 별도로 필요하다.

## 5. 테스트와 개선 결과 — 20%

Windows PowerShell과 Temurin JDK 17.0.20.1에서 `powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test`를 실행했다. 최종 출력은 **기능 181개·Swing 200개 통과, 종료 코드 0**이다. 별도 GUI 렌더에서도 Swing 200개가 통과했다. 렌더의 검사 수는 합계 381개에 중복 계산하지 않는다. 사용자 `data/`는 사용하지 않고 임시 데이터로 검사했다.

| 조건 | 기대 결과 | 실제 결과 |
|---|---|---|
| 1~5명과 7명 | 인원에 따라 전원 응답·찬성 2/3 기준 변경 | 1명·5명·7명 추천, 1명·2명 저장 복원, 같은 파트 재추가 통과 |

첫 GUI 재검사는 기능 179개를 통과했지만 선택기 갱신 중 `ArrayIndexOutOfBoundsException`으로 실패했다. 달력의 멤버 배열을 먼저 바꾸도록 수정한 뒤 재실행했고, 사유 보존 조건을 더한 최종 381개 검사가 통과했다([검증 기록](VERIFICATION.md)). 자동 검사는 실제 네이티브 확인창의 마우스 승인·취소, 다른 PC/DPI, 여러 창의 동시 저장을 검증하지 않는다.

## 6. 실행 및 사용 안내 — 10%

Windows PowerShell과 JDK 17 이상이 필요하다. `run-gui.ps1`이 있는 폴더에서 실행한다.

```powershell
java -version
javac -version
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test
powershell -NoProfile -ExecutionPolicy Bypass -File .\run-gui.ps1 -Demo
```

`-Demo`는 처음 실행할 때만 별도 `data/demo.properties`에 가상 데이터를 만들고 이후에는 기존 내용을 읽는다. 일반 실행 `.\run-gui.ps1`은 `data/banddecision.properties`를 사용한다. 1~5명 밴드는 **밴드 설정 → 멤버 선택 → 선택 멤버 삭제**로 만든다. 시연은 날짜 응답·추천, 곡 투표·추천, 확정 계획 순서로 보여준다. 자세한 조작은 [README](../README.md)에 있다.

현재 남은 검증은 학생 본인의 Demo 직접 시연, 동료 검토와 다른 PC 확인이다.

처음 사용하는 순서는 **밴드 설정에서 인원·실력 확인 → 사이드바 멤버 선택 → 달력 하루/기간/이 달 전체 선택 후 가능·불가 적용 → 곡·투표에서 곡 등록과 찬반 입력 → 합주 계획에서 추천 결과·장소 확인 후 확정**이다. 일부 불참이면 동의 여부를 확인한다. 계획 목록에서 수정·삭제할 수 있다. `java` 또는 `javac`가 인식되지 않으면 JDK 17 이상 설치와 PATH를 확인하고 새 PowerShell에서 실행한다.

## 7. 현재 범위와 향후 확장 계획

현재는 한 담당자가 한 PC에서 멤버 응답·투표를 입력하고 합주를 확정하는 범위까지 구현했다. 아래 기능은 미구현이며, 12주차 가이드의 ‘현재 범위와 확장계획’에 따라 생략 이유와 후속 방향을 정리했다. 제출 전에는 새 기능 추가보다 직접 시연과 발견 오류 수정을 우선한다.

| 우선순위·확장 기능 | 현재 생략한 이유 | 구현 방향과 확인 기준 |
|---|---|---|
| 1. 첫 실행 시 밴드 구성 | 기본 6명에서 추가·삭제하는 방식으로 핵심 흐름을 먼저 완성 | 시작 화면에서 인원·이름·파트 입력 후 생성. 1명·5명·같은 파트 중복 구성과 재실행 복원 확인. |
| 2. 합주 시간·장소 중복 확인 | 응답은 날짜 단위, 합주 시간은 20~22시 고정 표시. 시간별 응답은 별도 정책 필요 | 시작·종료 시각을 직접 입력·저장하고 같은 시간·장소 충돌 안내. 겹치는 시간 경고와 연속 시간 허용 검사. |
| 3. 확정 계획 공유 | 현재는 담당자가 로컬 화면에서 확인하는 사용 방식 | 일정·곡·장소를 텍스트 또는 일정 파일로 내보내기. 내보낸 내용이 확정 스냅샷과 같은지 확인. |
| 4. 멤버별 온라인 응답 | 로그인·권한·서버 저장·동시 수정 처리가 필요해 수업 제출 범위를 넘음 | 멤버 고유 ID와 서버 저장을 도입하고 본인 응답만 수정하도록 권한 분리. 두 사용자의 동시 입력과 타인 응답 수정 거부 검증. |

온라인 확장에서는 현재의 배열 인덱스 연결을 고유 멤버 ID 연결로 바꾸고 파일 저장 책임을 서버 저장과 분리할 필요가 있다. 기존 v3 데이터의 이전과 확정 계획 스냅샷 보존도 함께 검증해야 한다. 위 항목은 후속 제안이며 구현 완료 기능이나 확정된 개발 일정으로 보지 않는다.
