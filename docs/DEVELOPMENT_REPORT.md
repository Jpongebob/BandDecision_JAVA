# BandDecision 개발 문서

문서 수정: 2026-11-20 · 구현·자동 검사 확인: 2026-11-19 · Java 17 Swing 데스크톱 앱

BandDecision은 **밴드의 합주 날짜와 곡을 함께 정하는 프로그램**이다. 담당자가 멤버의 일정과 투표를 입력하면 참석 인원과 연주 부담을 계산해 추천한다. 최종 결정은 담당자가 내린다.

발표에서는 `-Demo`로 준비한 예시 데이터를 사용한다. 아래에는 이 프로그램이 필요한 이유와 구현한 기능, 수정 과정, 실행 방법을 정리했다.

## 1 문제와 사용자 시나리오

평가 비중 15%

### 해결하려는 문제

합주 날짜를 정할 때 가장 어려운 점은 멤버 모두가 가능한 날을 찾는 것이다. 답을 하지 않은 사람을 가능한 사람으로 세면 잘못된 날짜를 고를 수 있다. 곡도 찬성이 많다고 바로 정하기는 어렵다. 일부 멤버에게 너무 어려운 곡일 수 있기 때문이다.

그래서 날짜별 응답과 곡의 난이도를 함께 보고 결정할 수 있도록 했다. 처음 만든 콘솔 메뉴는 이 내용을 비교하기 불편해 달력과 표를 사용하는 GUI로 바꿨다. 확정 후 응답이 달라져도 이전 결정을 확인할 수 있도록 계획도 따로 저장한다.

### 대상 사용자

이 프로그램은 밴드에서 일정을 모으는 담당자가 사용한다. 멤버에게 받은 응답을 한 PC에서 대신 입력하는 방식이다. 처음에는 6명으로 시작하지만 추가하거나 삭제해 1~64명으로 사용할 수 있다. 기타 담당자가 두 명인 경우처럼 같은 파트를 여러 명이 맡아도 된다.

### 대표 사용 시나리오

| 사용자 행동 | 프로그램의 결과 |
|---|---|
| 달력에서 멤버별 가능·불가·미응답을 입력 | 그 날짜의 전원이 응답하면 가능 인원순으로 날짜 추천 |
| 후보곡 난이도와 멤버별 찬반을 입력 | 전원 투표와 찬성 기준을 충족한 곡을 추천 점수 내림차순으로 추천 |
| 추천 날짜·곡과 장소를 확인해 확정 | 참석·불참·사유·곡·장소를 당시 내용으로 보관 |

| R09 · P1 | 되돌리기 | 마지막 일정 응답 변경 한 건을 복원하고 저장. |

### 추천 규칙

날짜는 **가능 인원이 많은 순**, 인원이 같으면 **빠른 날짜순**이다. 다른 날짜에 미응답이 있어도 해당 날짜의 전원이 응답했다면 추천할 수 있다.

곡의 개인 부담은 `max(0, 난이도 - 멤버 실력)`이다. 개인 부담을 모두 더한 총부담으로 **추천 점수 = 3 × 찬성 수 - 2 × 총부담**을 계산한다. 높은 점수가 먼저다. 동점이면 찬성 수가 많은 곡, 총부담이 적은 곡, 내부 ID가 작은 곡 순이다.

### 검사 근거

기능 검사는 `AcceptanceTest`의 `smallBands()`, `dynamicMembers()`, `attendance()`, `songs()`, `songManagement()`, `plans()`, `planManagement()`, `persistence()`에 있다. 화면 연결과 되돌리기는 `GuiSmokeTest`와 그 안의 `completionAndUndo()`에서 검사한다. 추천 구현은 `DateRecommender`·`SongRecommender`, Demo 생성은 `DemoData`에 있다.

| 구성요소 | 책임 |
|---|---|
| `Main`, `DataStore` | 실행 모드에 맞는 파일을 읽거나 생성하고 변경 내용을 안전하게 저장 |

| `BandDecision`, `RehearsalPlan` | 멤버 관리, 확정 직전 재검증, 확정 당시 계획 스냅샷 보관 |

### 데이터의 관계

멤버 정보와 일정·투표는 배열의 같은 위치로 연결한다. 예를 들어 세 번째 멤버의 응답과 곡 난이도는 각각의 배열에서도 세 번째 위치에 있다. 멤버를 삭제할 때 한 배열만 바꾸면 다른 사람의 자료와 섞이므로, 관련 배열에서 같은 위치를 함께 제거한다.

확정 계획은 당시 내용을 복사해서 보관한다. 이 복사본을 스냅샷이라고 한다. 이후 멤버나 응답을 바꿔도 이미 확정한 계획은 그대로 남는다. 파일에는 멤버 수·날짜·곡·계획을 v3 형식으로 저장한다.

### 입력에서 저장까지

실행 흐름은 **파일 읽기 → GUI 입력 → 날짜·곡 추천 → 담당자 최종 확인 → 확정 계획 저장**이다. 개인의 ‘응답 완료’는 오늘~다음 달 말일 전체를 답했는지, 날짜 추천은 해당 날짜에 전원이 답했는지를 각각 판단한다.

| 단계 | 요청과 상태 변화 |
|---|---|
| 응답 입력 | 6명 중 마지막 미응답 멤버가 ‘가능’을 입력한다. 화면이 `AttendanceService`의 해당 날짜·멤버 응답을 바꾼다. |
| 추천 갱신 | `DateRecommender`가 전원 응답과 가능 인원을 계산해 반환하고 화면이 갱신된다. |
| 최종 확인 | `BandDecision`이 날짜·곡 ID로 미리보기를 만든다. 담당자가 확인한 뒤 조건을 다시 검증한다. |
| 확정·저장 | 조건을 충족하면 `RehearsalPlan`을 보관하고 `DataStore`가 저장한다. 취소나 조건 위반이면 새 계획을 만들지 않는다. |

## 6 실행 및 사용 안내

평가 비중 10%

### 실행 준비

Windows PowerShell과 JDK 17 이상이 필요하다. 외부 Java 라이브러리는 필요하지 않다. `run-gui.ps1`이 있는 폴더에서 실행한다.

```powershell
java -version
javac -version
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test
powershell -NoProfile -ExecutionPolicy Bypass -File .\run-gui.ps1 -Demo
```

### Demo와 저장 파일

`-Demo`는 처음 실행할 때만 별도 `data/demo.properties`에 가상 데이터를 만들고 이후에는 기존 내용을 읽는다. 일반 실행 `.\run-gui.ps1`은 `data/banddecision.properties`를 사용한다. 1~5명 밴드는 **밴드 설정 → 멤버 선택 → 선택 멤버 삭제**로 만든다. 시연은 날짜 응답·추천, 곡 투표·추천, 확정 계획 순서로 보여준다. 자세한 조작은 [README](../README.md)에 있다.

현재 남은 검증은 학생 본인의 Demo 직접 시연, 동료 검토와 다른 PC 확인이다.

### 처음 사용하는 순서

| 순서 | 화면에서 할 일 |
|---|---|
| 1. 밴드 설정 | 인원·이름·파트·실력을 확인한다. |
| 2. 일정 | 사이드바에서 멤버를 고른다. 달력 하루·기간·이 달 전체를 선택한 뒤 가능·불가를 적용한다. |
| 3. 곡과 투표 | 후보곡과 멤버별 난이도를 입력하고 찬반을 저장한다. 반대에는 사유를 적는다. |
| 4. 합주 계획 | 추천 날짜·곡과 장소를 확인한다. 부분 참석이면 동의 후 확정한다. 목록에서 수정·삭제한다. |

### 실행 문제 확인

 `java` 또는 `javac`가 인식되지 않으면 JDK 17 이상 설치와 PATH를 확인하고 새 PowerShell에서 실행한다.

## 7 현재 범위와 향후 확장 계획

현재는 담당자 한 명이 PC에서 응답과 투표를 입력하고 합주를 확정할 수 있다. 아래 기능은 아직 만들지 않았다. 지금 방식에서 불편할 수 있는 부분과, 이후 보완할 방법을 우선순위대로 정리했다. 제출 전에는 기능을 더 늘리기보다 직접 시연하면서 오류를 확인하는 일이 먼저다.

| 우선순위·확장 기능 | 현재 생략한 이유 | 구현 방향과 확인 기준 |
|---|---|---|
| 1. 첫 실행 시 밴드 구성 | 기본 6명에서 추가·삭제하는 방식으로 핵심 흐름을 먼저 완성 | 시작 화면에서 인원·이름·파트 입력 후 생성. 1명·5명·같은 파트 중복 구성과 재실행 복원 확인. |
| 2. 합주 시간·장소 중복 확인 | 응답은 날짜 단위, 합주 시간은 20~22시 고정 표시. 시간별 응답은 별도 정책 필요 | 시작·종료 시각을 직접 입력·저장하고 같은 시간·장소 충돌 안내. 겹치는 시간 경고와 연속 시간 허용 검사. |
| 3. 확정 계획 공유 | 현재는 담당자가 로컬 화면에서 확인하는 사용 방식 | 일정·곡·장소를 텍스트 또는 일정 파일로 내보내기. 내보낸 내용이 확정 스냅샷과 같은지 확인. |
| 4. 멤버별 온라인 응답 | 로그인·권한·서버 저장·동시 수정 처리가 필요해 수업 제출 범위를 넘음 | 멤버 고유 ID와 서버 저장을 도입하고 본인 응답만 수정하도록 권한 분리. 두 사용자의 동시 입력과 타인 응답 수정 거부 검증. |

여러 사람이 온라인으로 사용하려면 배열 위치 대신 멤버마다 고유 번호를 부여해 자료를 연결해야 한다. 파일 저장을 서버 저장으로 바꾸는 작업도 필요하다. 이때 기존 v3 파일을 옮겨도 응답과 확정 계획이 유지되는지 확인해야 한다. 위 내용은 앞으로의 보완 방향이며, 구현을 마친 기능은 아니다.
